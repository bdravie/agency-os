# Event listing to social post queue (demo)

**Outcome:** every newly published event listing turns into a ready-to-approve Facebook and Instagram post, with an image and a link back to the listing, so events get promoted without anyone writing posts by hand, and without double posting or silent failures.

**This is a demo.** It runs on made-up motorcycle events and local stand-ins. It has not been run for a client and nothing in it is posted anywhere real.

**Who it's for:** a directory or community site that lists events (here, a Brilliant Directories site) and wants each new event shared on its social pages, with a person approving every post first.

## How it works

1. **New-event detection.** Every 5 minutes n8n reads the directory's listings (a mock feed in Brilliant Directories' field names) and keeps those that are published (`post_status` 1) and not already in the approval queue, the Posted log or the Failures tab. Unpublished listings and repeats are ignored.
2. **Posts.** Claude Haiku writes a Facebook post and a shorter Instagram caption from the listing fields only. Code then checks the reply (no links, no invented figures, length) and adds the listing's own link and the hashtags. The model never writes the link.
3. **Image.** A small Playwright script draws a square 1080 x 1080 card from the listing photo, event name, date and place (`scripts/render-card.mjs`).
4. **Approval queue.** The post, caption and image go into the queue as **Pending**. Setting a row to **Approved** is the only thing that triggers publishing.
5. **Publishing.** Every minute a second workflow takes Approved rows and sends each to the Page with Meta's photo-post call (`POST /{page-id}/photos` with `url` and `caption`). The Instagram request is prepared in the same shape and saved, not sent.
6. **No repeats, no silent failures.** The event ID is written to the Posted log and checked before every publish. A step that fails for one event writes a line to **Failures** (event, step, error) and the other events carry on; a run that stops outright is caught by a third workflow set as n8n's error workflow.

### What is real and what is a stand-in

| Part | In this demo | In a real build |
|---|---|---|

| Directory feed | Mock on 127.0.0.1 using Brilliant Directories' field names and reply envelope | The site's own API with its key |
| Approval queue, Posted log, Failures | Local board on 127.0.0.1 standing in for a Google Sheet | Google Sheets nodes |

| Instagram | Request prepared and saved only | Sent once a professional account is linked |

## Setup

Needs: Node (already here), `uv sync`, and `ANTHROPIC_API_KEY` in `.env` (or use `--no-llm`). No other account.

```
# 1. Start the demo board and helper (leave it running)
uv run python -m agency.event_social serve

# 2. Start n8n in a second Terminal window (first time: it asks you to make a local login)
npx n8n

# 3. First time only: load the three workflows
npx n8n import:workflow --separate --input=demos/event-listing-to-social-post-queue/n8n
```

- Board: http://127.0.0.1:8787  ·  n8n: http://localhost:5678
- `uv run python -m agency.event_social reset` empties the queue, logs and mock Page before a take.
- `uv run python -m agency.event_social serve --no-llm` uses rule-based wording: free and offline.
- To run without opening n8n: `npx n8n execute --id=EvtSocialQueue01` then `npx n8n execute --id=EvtSocialPublsh2` (with n8n itself stopped).
- The workflows are imported unpublished, so nothing runs on a timer until you press Publish in n8n. Publish all three to see the timers and the failure reporter work on their own.
- The workflow files are generated by `scripts/build-workflows.py`; edit there and re-run, then import again.

Checked on 12 Nov 2026 with n8n 2.47.5: first run queues 8 posts and logs the broken photo once; a repeat run adds nothing; approving one row posts it once; approving it again is marked "Already posted"; a refused publish and a stopped run both reach Failures. `uv run pytest tests/test_event_social.py` covers the wording checks and the sample data.

## Running cost per month

- **AI:** one short Haiku call per new event (a few hundred words in and out), so well under a penny per event; replies are cached in `.cache/`, so re-running the demo is free. Check the Anthropic usage page for the exact figure.
- **n8n:** £0 self-hosted (Community Edition, as here, or on the client's existing hosting). n8n Cloud is a paid monthly plan: check n8n's pricing page before quoting it.
- **Google Sheets and Drive, Meta Graph API:** no charge for this use.
- **Brilliant Directories API:** part of the site's admin area (Developer Hub); the documentation states no separate charge, to be confirmed on the client's plan.

## What data it touches

Business data only: event titles, dates, places, descriptions, photos and links that are already public on the directory. No organiser names, attendee details, emails or phone numbers are read or stored. The sample data is made up (`sample-data/listings.json`, drawn photos in `sample-data/photos/`).

## What I learned

Read on 12 Nov 2026 from each tool's own documentation. Not yet tried against a real Brilliant Directories site or a real Meta app.

**Brilliant Directories (new to me)**
- REST API at `https://<site>/api/v2/`, key sent in an `X-Api-Key` header, created in the admin area under Developer Hub and shown once. Keys can be limited to certain endpoints.
- Events are member posts in `data_posts`: `GET /data_posts/get` lists them, filtered with `property`, `property_value` and `property_logic`, 25 per page by default and 100 at most. Useful fields: `post_id`, `post_title`, `post_content`, `post_start_date`, `post_location`, `post_image`, `post_status` (0 draft, 1 published), `post_live_date`, `revision_timestamp`. Dates are `YYYYMMDDHHmmss`.
- Limit: 100 requests a minute for the whole site, all keys together. A poll every 5 minutes uses very little of it.
- It also has webhooks (set up in Developer Hub, used by its Zapier integration), but I found no documented event that fires exactly when a post is approved and published, so polling on `post_status` is the dependable route. To check on the real site: the `data_id` for Events, how the public link of a listing is built, and whether `post_image` is a file name or a full address.

**Meta Graph API (new to me)**
- Facebook Page photo post: `POST /{page-id}/photos` with `url` (an image Meta can fetch) and `caption`; it replies `{id, post_id}`. Needs a Page access token with `pages_manage_posts`, `pages_read_engagement` and `pages_show_list`, from someone who can create content on the Page. A bad image comes back as error 324.
- Instagram is two calls: `POST /{ig-user-id}/media` with `image_url` and `caption`, then `POST /{ig-user-id}/media_publish` with the `creation_id`. It needs a professional Instagram account, JPEG only, an image on a public address, and allows up to 100 API posts in 24 hours. Links in captions are not clickable.
- The main delivery risk: while the app is in development mode only people with a role on the app can grant it permissions, which is enough for a business posting to its own Page with its own admin. Serving other people's Pages needs Meta's App Review. Page tokens also expire unless a long-lived one is set up. Images must be on a public address, so a local or private Drive link will not do.
- The API itself is free.

**n8n (first time run here)**
- Version 2 separates saving from publishing: a workflow's timer only runs once it is published. An error workflow starts when a published workflow's run fails, not on a manual test run.
- "On error: continue (error output)" on a node sends a failed item down a second branch, which is how one broken event is logged while the rest carry on.
- Version 2 switches off the Execute Command node and blocks environment variables in Code nodes by default, so the image script is called over HTTP rather than as a shell command, and keys belong in n8n credentials.
- Self-hosted Community Edition is free with no sign-up.

## Copying for a new client

1. In workflow 1's Settings node, point `directory_api` at the site's API and move the key into an n8n credential; adjust the filter for their Events `data_id`.
2. Replace the `/sheet` calls with Google Sheets nodes (Queue, Posted, Failures tabs) and use a Google Sheets trigger on the Status column.
3. Save cards to Google Drive (or the site's own hosting) at an address Meta can reach.
4. In workflow 2's Settings node, set `graph_url` to `https://graph.facebook.com/v27.0`, the Page ID, and a Page access token held in a credential. Test on a test Page first.
5. Edit `prompts/event-social-post.md` for their tone and change the card colours in `scripts/render-card.mjs`.
